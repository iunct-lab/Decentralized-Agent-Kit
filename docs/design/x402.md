# x402: HTTP 402 の支払い要求を DAK に取り入れるか

PBI #306（元要望 #30）。x402 の 402 応答を DAK の「支払いが要る」Observation として受け取り、
エージェントが払うと決めたときだけ再試行する形が DAK に合うかを、仕様と試作（#307、
`agent/dak_agent/payments/x402.py`）をもとに判断するための文書。採否と対応ネットワークは利用者が決めた（「決定」節）。

## 仕様の要約（2026-09-29 に一次資料で確認）

- 現行は v2（`x402Version: 2`）。HTTP では、サーバは 402 と一緒に `PAYMENT-REQUIRED` ヘッダ（`PaymentRequired` の JSON を base64）を返す。
  クライアントは `PAYMENT-SIGNATURE` ヘッダ（`PaymentPayload` の JSON を base64）を付けて再送し、サーバは `PAYMENT-RESPONSE` ヘッダ
  （`SettlementResponse` の JSON を base64）で決済の結果を返す。x402 の情報はすべてヘッダで運び、本文はサーバの自由
- v1 は要求を 402 の本文（JSON）に入れ、`X-PAYMENT` / `X-PAYMENT-RESPONSE` ヘッダを使う。金額は `maxAmountRequired`、
  ネットワークは `base-sepolia` のような名前、`resource`（URL）は要求ごと。v2 は `amount`、CAIP-2（`eip155:84532`）、`resource` は応答に 1 つ
- `PaymentRequired.accepts` の各要素（`PaymentRequirements`）: `scheme`、`network`、`amount`（最小単位の整数の文字列）、`asset`、
  `payTo`、`maxTimeoutSeconds`、`extra`（方式ごと。EVM の `exact` なら EIP-712 のドメイン名・版）
- `PaymentPayload`: `x402Version`、`accepted`（選んだ `PaymentRequirements` をそのまま返す）、`payload`（方式ごとの署名。EVM の
  `exact` なら EIP-3009 の authorization と EIP-712 署名）、任意で `resource` と `extensions`
- 方式は `exact`（固定額）が中心。公開ファシリテータは `upto`・`batch-settlement` も出している（下の `/supported`）
- 検証と決済はファシリテータ（`/verify`、`/settle`、`/supported`）が担う。公開ファシリテータ `https://x402.org/facilitator` は
  開発・テストネット向けで、本番のメインネットには使わないよう文書が明記している
- `https://x402.org/facilitator/supported`（2026-09-29 に GET）の v2 の `exact`: `eip155:84532`（Base Sepolia）、
  `solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1`（Solana devnet）、`stellar:testnet`、`algorand:…`、`aptos:2`、`hedera:testnet`、`xrpl:1`。
  v1 は `base-sepolia` と `solana-devnet`

## 今の DAK の流れとの対応

今の DAK の支払いは独自の流れ（`AGENTS.md` §5）。有料ツールは例外で「支払いが要る」を知らせ、証明は SOL の送金のハッシュ。

| x402 の要素 | 今の DAK | 試作（#307） |
|---|---|---|
| 402 と `PAYMENT-REQUIRED`（何を・いくら・誰に） | `PaidToolWrapper`（`agent/dak_agent/decorators.py`）が `PaymentRequiredError`（`price`、`address`、`currency`、`message`。`agent/dak_agent/errors.py`）を投げる。HTTP は使わない | `parse_payment_required` が v2 のヘッダと v1 の本文を `X402Requirement` にする |
| 要求を Observation にする | `AdaptiveAgent._on_tool_error`（`agent/dak_agent/adaptive_agent.py:483-498`）→ `PaymentHandler.format_payment_error`（`agent/dak_agent/handlers/payment_handler.py`）が `{"error": ...}` を返す | `format_x402_observation` が同じ `{"error": ...}` の形で支払い方法を列挙する。支払いは勧めない |
| 支払う（署名） | エージェントが `send_sol_payment`（`agent/skills/solana_wallet/tools.py:57`）でネイティブの SOL を送る。鍵は `SOLANA_PRIVATE_KEY` | `retry_with_payment(..., approved=True)` だけが mock の `payload` を作る。鍵は使わない |
| `PAYMENT-SIGNATURE` で再送 | エージェントが元のツールを `payment_hash` 引数を付けて呼び直す | `PAYMENT-SIGNATURE` ヘッダを付けて同じ URL に 1 回だけ再送する |
| ファシリテータの `/verify`・`/settle` | ツール側が `verify_transaction` で RPC に問い合わせる（`agent/dak_agent/wallets/solana_wallet.py:178`） | 無い（偽の有料サーバが 200 を返すだけ） |
| `PAYMENT-RESPONSE`（決済の結果） | 無い（ツールの戻り値だけ） | 読まない（テストでヘッダの中身を確かめただけ） |

違いの要点:

- **証明の中身が違う**。今の DAK は「もう送った」送金のハッシュを渡す（送金が先、検証が後）。x402 は「送ってよい」という署名済みの authorization を渡し、
  ファシリテータが検証して決済する（署名が先、送金はサーバ側）。x402 の署名は再送時にだけ意味を持ち、単独のツールとして「送金」を先に済ませる形にはならない
- **資産が違う**。今の DAK はネイティブの SOL。x402 の `exact` は主にトークン（EVM は EIP-3009 対応の USDC など、Solana は SPL トークン）
- **自称と実態のずれ**。`agent/skills/solana_wallet/tools.py` などは「AP2/x402」と名乗るが、x402 のヘッダ・ペイロードには従っていない（試作の前からの事実）

## 設計原則との関係

- **SDK の「402 を見て自動で払う」使い方は採らない**（設計原則 1: System ENABLES, Agent DECIDES）。Python SDK の httpx / requests
  向けのクライアントは、402 を受けると登録した方式で署名して再送する。これは利用者に黙って払う形になる
- **402 は Observation として返し、再送はエージェントの明示的な判断でだけ行う**。試作は `approved` を既定値なしのキーワード専用引数にし、
  `True` 以外なら送信も署名もしない（`test_no_approval_sends_nothing`、`test_non_boolean_approval_sends_nothing`）
- 「承認」を誰がどう与えるかは試作では決めていない。実装するなら、支払いのツールの呼び出しを、ツールの呼び出しごとに許可・確認・拒否を決める
  `PermissionPlugin`（`agent/dak_agent/permission.py`、`docs/design/permission-boundary.md` の「決定」）で止める。既定の規則（`DEFAULT_RULES`）は
  `local`（組み込み・スキルのローカルツール）を allow にしているので、支払いのツールに `ask` の規則を明示的に足さないと確認なしで動く。
  ツールの中に独自の確認を作らない（権限の判断を 1 か所に置く決定と食い違う）。確認を通って実行されたときだけ、ツールが `approved=True` で `retry_with_payment` に当たる処理を呼ぶ
- **Verifiable Intent（PBI #301）との接点**: #301 は、利用者が署名した意図（金額の上限・宛先）を超える送金を理由付きで止める。x402 の支払いにも当てるなら、
  検証に使う値は `PaymentRequirements` の `amount`（最小単位）・`asset`・`network`・`payTo`。署名の前（`retry_with_payment` に相当する所）で
  意図と突き合わせ、外れたら署名せず Observation を返す。単位（最小単位の整数とトークンの種類）を意図の側でも同じに扱う必要がある。
  SDK の `spend_controls`（1 回の上限、許可する資産）や `on_before_payment_creation` の hook は同じ場所に当たるが、利用者が署名した意図ではなく
  クライアントの設定なので、#301 の代わりにはならない

## Python SDK を使うか、自前か

| 観点 | SDK `x402`（2.24.0） | 自前（試作の形） |
|---|---|---|
| 依存の量 | 本体は `pydantic`・`typing-extensions`・`nest-asyncio`。署名には extra が要る: `x402[svm]` は `solana`・`solders`（DAK に既にある）、`x402[evm]` は `web3`・`eth-account` など | 追加なし（`httpx` は今の依存から推移で入っている） |
| v1 / v2 | 両対応（`python/x402/legacy` もある） | 試作は両方を読み、送るのは v2 だけ |
| 本物の署名 | 方式ごとの実装がある（`mechanisms/evm`・`svm`・`tvm`）。EIP-712 / EIP-3009、SPL の transfer を自分で書かずに済む | 自分で書く必要がある。署名の形を間違えるとファシリテータに拒まれ、仕様の変化にも追従し続けることになる |
| 自動で払わない形にできるか | できる。httpx のラッパーを使わず、`x402ClientSync.create_payment_payload(payment_required)` を承認後にだけ呼ぶ | そのまま（試作がその形） |
| safe-chain の最小経過日数 | 2.24.0 は公開 2026-09-22。更新が速い（2.4.0〜2.9.0 が 2026-03〜04 の 6 週間）ので、最新版は経過日数のゲートに掛かりやすい。1 つ前の版を固定して入れる運用になる | 関係しない |
| ライセンス | MIT（PyPI）。リポジトリは Apache-2.0。どちらも DAK と両立 | — |

提案: **402 の解析と Observation は自前（試作のまま）、本物の署名だけ SDK の方式の実装を使う**。解析は小さく、DAK の Observation の形に合わせる必要がある。
署名は暗号の細部が多く、自前で持つ利点が無い。SDK は `create_payment_payload` だけを使い、HTTP のラッパーは使わない。

### 本物の署名に要るもの（採用後の実装 PBI の前提）

- **テストネット**: 公開ファシリテータで試せるのは Base Sepolia（`eip155:84532`）と Solana devnet（`solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1`）など（上の `/supported`）。
  どちらもテスト用のトークン（USDC）を faucet で得る必要がある。公開ファシリテータに手数料がかかるかは**未確認**（文書に料金の記載を見つけられなかった）
- **署名の鍵**: 環境変数から読み、ファイル（スクリプト・テスト・ドキュメント・設定）に置かない（CLAUDE.md の規約）。Solana なら今の `SOLANA_PRIVATE_KEY` と
  同じ扱い。EVM なら新しい環境変数が要る。鍵を持つのは agent のコンテナだけにする
- **ファシリテータ**: テストネットは公開ファシリテータ。メインネットは別途（本 PBI の範囲外、実資金は使わない方針）
- **統合テスト**: fake-LLM の統合構成（`docker-compose.test.yml`）に、`PAYMENT-REQUIRED` を返す偽の有料サーバと、`/verify`・`/settle` を返す偽のファシリテータを置けば、
  実ネットワークなしで決定論的に試せる

### 確かめられなかったこと（未確認）

- 公開ファシリテータ（`x402.org/facilitator`）の料金・利用制限
- SDK の `svm` の方式がネイティブの SOL を扱えるか（`exact` の Solana 実装は SPL トークン前提に見える。コードを読み切っていない）
- SDK の `create_payment_payload` を `extensions` 付きの要求に使ったときの挙動

## 採用するなら: 次の実装 PBI の範囲（案）

1. 支払いのツール `pay_x402(url, option_index)` を登録し、`DEFAULT_RULES` に `Rule("local", "pay_x402", "*", "ask")` を足す（`PermissionPlugin` の確認を
   通ったときだけ実行される）。継続許可（`always`）を支払いにも効かせるかはその PBI で決める。ツールは実行されたら SDK の方式で署名して `PAYMENT-SIGNATURE` で再送する。402 を受けた時点では何も払わない（試作の `parse_payment_required` と `format_x402_observation` を使う）
2. 外部の有料 HTTP リソースを取るツール（例: `fetch_url`）が 402 を受けたら、試作の Observation を返す
3. 統合構成に偽の有料サーバと偽のファシリテータを足し、「402 → Observation → 承認なしなら送らない / 承認ありなら 1 回だけ再送」を統合テストで確かめる
4. 対応ネットワークは 1 つから（下の「決定」で Solana devnet）。鍵は環境変数から
5. 既存の独自の流れ（`PaidToolWrapper` と `payment_hash`）は残す（DAK 内部の有料ツール向け）。x402 に寄せるかは 1〜4 の後に別に判断する

MCP サーバや BFF に 402 を返す有料エンドポイントを作る（DAK が売る側になる）ことは、上とは別の PBI にする。

## 採用しないなら

- 理由を残し、#307 の試作（`agent/dak_agent/payments/`、`agent/tests/test_x402_prototype.py`）は消す（ツールに登録しておらず、どこからも使われていないので、残すと保守だけが残る）
- 「AP2/x402」と名乗っている記述（`agent/skills/solana_wallet/tools.py` など）から x402 を外す
